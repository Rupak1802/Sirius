Appendix — AI Prompts and Example Outputs 1. Introduction and Purpose ANCHOR is an adaptive fintech product concept for workers whose income is irregular by design. The system continuously interprets income patterns, essential obligations, liquidity and recovery behavior to decide what the worker should save, protect, pause, repay or borrow. The uploaded pitch deck positions ANCHOR as a financial resilience engine that moves from static scoring and forecasting to adaptive orchestration, measured in days of runway rather than a static balance. (Source: ANCHOR Pitch Deck, opening/product-positioning section) The uploaded UI/UX specification describes the intended experience as a modern, trustworthy, human, simple, mobile-first fintech companion that continuously understands income, predicts financial stress, recommends savings, protects essential work-related expenses, supports multiple income sources and offers responsible emergency support. It also specifies icon-first, voice-narrated, jargon-free interactions. (Source: MITRA Master UI/UX Design Prompt, Design Philosophy and product experience sections) (Source: MITRA Master UI/UX Design Prompt, inclusion and accessibility requirements) This SRS translates those product principles into implementable requirements for a 24-hour hackathon prototype. It is intentionally optimized for a working demo rather than a production banking system. 1.1 SRS goals Provide a single source of truth for all MVP pages, navigation, states, interactions and AI behavior. Define deterministic financial logic so the AI layer explains and personalizes decisions without autonomously inventing monetary actions. Enable a 2–3 minute live demo in which a bad-earnings scenario visibly changes the user’s financial state and the system responds. Preserve a clear path to later bank, UPI, Account Aggregator and gig-platform integrations while using mocked data for the hackathon. 2. Product Vision and Objectives Core positioning: “Your balance tells you how much money you have. ANCHOR tells you how long your life stays financially safe.” Objective Requirement Prevent avoidable financial fragility Detect likely stress before a worker becomes unable to cover essential obligations. Make banking adaptive Recompute the financial state whenever income or spend changes and adjust actions accordingly. The pitch deck explicitly calls for a state to be re-computed on every transaction. (Source: ANCHOR Pitch Deck, state-machine and resilience section) Prioritize ability to keep earning Protect rent, fuel, phone and vehicle-related funds before optional actions. (Source: ANCHOR Pitch Deck, resilience measurement and essentials-first behavior) Make financial guidance accessible Use rupees and days rather than abstract financial ratios, with optional voice narration and plain-language explanations. (Source: MITRA Master UI/UX Design Prompt, inclusion and accessibility requirements) Support responsible credit Calculate the smallest useful emergency gap instead of promoting unnecessarily large borrowing. (Source: MITRA Master UI/UX Design Prompt, responsible emergency support) Turn volatility into an advantage Use income trend, volatility and recovery behavior as signals for adaptive savings, protection and planning. 3. Scope and Release Boundaries 3.1 In scope for the 24-hour MVP Onboarding for worker type, income sources and priorities. Home dashboard with safe-to-use money, current financial state, weekly income/expense/savings/upcoming summaries. Earnings page with platform-level gross, work costs, real profit and profit/hour. Money Plan with adaptive allocation into essentials, work expenses, savings, emergency reserve and flexible spending. Smart Savings with a dynamically recommended amount. Financial Weather with day-by-day forecast and a “tight day” alert. What-If simulator for income drops, inability to work, bike repair and other shocks. Emergency support analysis that recommends only the calculated gap. Protect My Income reserve for fuel, phone, vehicle and emergency work-enabling costs. Personalized Coach using the deterministic financial context plus an LLM for explanation and conversational phrasing. Opportunity Engine for mocked live platform-rate comparisons. Growth Engine for a mocked surplus-only growth recommendation, with hard safety caps. Planning Engine for “what if I don’t work for N days?” scenarios. Weekly review, notifications and profile/settings. State-machine animation and demo simulation controls. 3.2 Explicitly out of scope for MVP Real bank login or credential handling. Real money movement. Real loan origination, KYC or underwriting approval. Production UPI/UPI Autopay execution. Production Account Aggregator consent flows. Live gig-platform APIs unless a stable public/mock endpoint is immediately available. Production insurance issuance or claims. Model training from proprietary datasets. Native iOS/Android apps. 4. Essentials before goals: protect what enables housing, mobility, communication and earning. 3. Days and rupees, not jargon: users should understand the recommendation immediately. 4. AI explains; rules control: monetary actions are deterministic and auditable. 5. Credit last: use savings, protection and plan adjustments before debt. 6. One primary action per screen: thumb-sized and easy to understand. 7. Calm, not alarming: visual states should communicate safety/confidence rather than financial anxiety. The UI prompt explicitly calls for calm, safety and confidence. (Source: MITRA Master UI/UX Design Prompt, product experience/design tone) 8. Demo-first reliability: simulated data and deterministic scenarios must work offline or with minimal dependencies. 6. The LLM MUST NOT approve or deny credit. Credit amount comes from deterministic shortfall/recovery rules. The LLM MUST NOT invent income, obligations, rates or transactions. The LLM MUST distinguish simulated/demo data from real data when relevant. The LLM SHOULD answer in plain language and avoid ratios or financial jargon on the user surface. When context is insufficient, the LLM SHOULD say what is unknown rather than guessing. 7.5 Recommended prompts Recommendation explainer prompt System: You are ANCHOR, an explainable financial resilience assistant. Explain only the structured decision supplied by the policy engine. Never invent transactions or financial values. Give: WHAT, WHY, WHAT HAPPENS NEXT. Use short sentences, rupee amounts and day counts. Coach prompt System: Answer the user question using the provided financial context. Prefer a conservative, essentials-first answer. If the request would cause a prohibited action, explain the safer alternative. Do not recommend borrowing more than the calculated gap. 8. Financial Resilience State Machine The ANCHOR pitch deck defines the state machine as STABLE → CAUTION → FRAGILE → SHOCK → RECOVERY, with re-evaluation whenever income or spending changes. (Source: ANCHOR Pitch Deck, state-machine definition) State Meaning System behavior Primary user message STABLE Healthy buffer; good time to save Save more when surplus exists; growth may be enabled under caps; opportunity suggestions allowed “You are in a comfortable position this week.” CAUTION Earnings dip / pressure emerging Increase liquidity; ring-fence essentials; reduce savings target “This week may be tighter. Keep essentials protected.” FRAGILE Buffer thin Protect rent + fuel + work enablers; pause optional growth; restrict new borrowing “Money is tight this week. I have protected your essentials.” SHOCK Emergency or severe shortfall Must-pay bills only; calculate actual gap; offer only constrained bridge “A shortfall is likely. Here is the smallest gap to cover.” RECOVERY Income/buffer rebuilding Gradually resume savings and growth; rebuild resilience buffer before discretionary expansion “You are recovering. Let us rebuild your buffer first.” 9. Business Rules and Core Algorithms 9.1 Income baseline Baseline weekly income = median of the last N comparable weekly earning periods. For the hackathon, use N = 4–8 weeks and prefer median over mean to reduce distortion from unusually strong shifts. 9.2 Income volatility Volatility indicator = standard deviation of weekly income / mean weekly income. Keep this internal; surface only plain-language effects such as “your earnings are less predictable than usual.” 9.3 Runway in days Runway days = available protected/unrestricted funds that can legitimately cover essentials ÷ expected daily essential outflow. The exact production definition can evolve; the MVP must keep the displayed number consistent across dashboard, What-If and Emergency screens. 9.4 Coverage Coverage = (available money + conservative near-term predicted income) / essential obligations due within the forecast window. The internal value may use ratios, but the interface shows only rupees and days. 9.5 Recovery velocity Recovery velocity = typical time to return from a low-income period to personal baseline. In MVP, approximate from the shortest recent recovery windows or use a deterministic fixture per persona. 9.6 Example state policy thresholds Rule Threshold example Effect Stable coverage &gt;= 1.50 and low shock risk Save recommended; growth may activate. Caution coverage 1.15–1.49 Reduce savings intensity; preserve liquidity. Fragile coverage 0.85–1.14 Protect essentials; pause optional growth. Shock coverage &lt; 0.85 or severe event Must-pay only; compute smallest useful bridge. Recovery coverage improving across 2+ periods Resume buffer rebuilding, then savings/growth. These thresholds are MVP heuristics, not production lending policy. They exist to make the demo deterministic and easy to audit. 9.7 Opportunity Engine rules Today’s platform rate &lt; 70% of that platform’s recent average. Alternative connected platform rate &gt;= 120% of current platform rate. Estimated incremental earnings meaningfully improve the active goal gap. User is not in a state where platform-switching would conflict with a safety action or work constraint. 9.8 Growth Engine rules If state is FRAGILE or SHOCK: investment = ₹0. If any net-negative earning day occurs: investment = ₹0 for that day. Else investment = min(30% of surplus, ₹100/day). Never use protected essentials to fund growth. 9.9 Emergency support rules Recommended support = max(0, emergency cost − available savings that can safely be used − conservative near-term income before the obligation). If the gap is zero, the system should recommend using existing resources instead of borrowing. 10. Security, Privacy and Responsible Finance 16.1 MVP controls Use synthetic/demo financial data only. No collection of bank passwords, debit-card details or real KYC documents. Keep LLM/API secrets server-side. Log every simulated financial action with reason and state. Provide a visible explanation for automated recommendations. Provide a user override for simulated actions such as savings/protection where practical. Clearly label credit as simulated support in the hackathon demo. 16.2 Responsible-credit principles 1. Prefer using existing safe liquidity before new debt. 2. Never recommend more support than the calculated need without a deliberate user choice. 3. Show transparent repayment preview before simulated acceptance. 4. Never describe a model output as a guaranteed approval or guaranteed income event. 5. Use explainable features and avoid sensitive personal attributes in the prototype decision logic. 17.
